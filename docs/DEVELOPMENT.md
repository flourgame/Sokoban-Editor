# 开发过程

项目围绕两条流程展开：玩家完成「选关 → 推箱 → 通关 → 下一关」，关卡制作者完成「编辑 → 求解 → 试玩 → 公开」。以下按实际设计与迭代记录整理，阶段截图展示当时的实现，当前界面见[操作手册](USER_MANUAL.md)。

| 阶段 | 主要工作 | 设计取舍 |
| --- | --- | --- |
| 规则与流程 | 整数格棋盘、推箱规则、撤销、选关和结算 | 规则独立于场景与动画，求解、试玩复用同一关卡数据 |
| 编辑器 0.3.x | 画布、工具栏、选择与多页签布局 | 把文档状态和界面状态分开，减少切换关卡时丢失内容 |
| 求解 0.4 | 推箱状态搜索、完整路径与回放 | 明确先优化推箱次数，再优化移动次数，让策划能解释结果 |
| 生成与视野 0.5.x | 生成方案探索、大地图跟随与整图视野 | 制作工具可以处理大地图，游玩时仍保持可读的格子尺寸 |
| 生成 0.12–0.13 | 从候选变异探索转向逐步构造实现 | 单关与批量共用生成核心，保留参数和解答便于复现与筛选 |
| 表现 0.14.x | 游戏场景与格子预制体、连续输入、音效与转场 | 将逻辑落位与视觉过渡分离，兼顾操作响应与表现调整 |
| 完整工作流 | 分类公开、批任务、印章与保存保护 | 从单张地图绘制扩展到内容生产与维护 |

## 编辑工具如何形成完整流程

初期重点是画布和笔刷；增加框选、剪贴板与多页签后，编辑操作开始涉及多个状态。随后把关卡、印章文档、撤销记录及未保存提示统一到会话中，再接入求解、试玩、生成与管理页面，让关卡制作能够在游戏内完成。详见[编辑器演进](development/EDITOR.md)。

## 算法如何服务关卡设计

求解结果既用于检查可解性，也为回放、生成筛选和关卡指标提供依据。生成策略经过多次迭代，当前使用逐步构造与求解反馈，并将推箱范围、复杂度和质量分开处理，避免用单一数字代替全部关卡体验。详见[求解与生成](development/GENERATION.md)。

## 表现如何保持规则稳定

角色与箱子的规则坐标立即更新，表现组件负责移动、倾斜、缩放和反馈。按钮的视觉层与点击范围分开，动画开关统一控制视觉时间和过渡收尾，因此关闭动画后仍能正常移动、计时、求解和回放。详见[表现层演进](development/PRESENTATION.md)。
