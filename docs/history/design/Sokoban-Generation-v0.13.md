## 生成流程

1. 复制参数，以现有 `System.Random(seed)` 创建随机序列。建立带外围墙的空房间，先随机 y、再随机 x 放置玩家，保存初始布局。
2. 根据当前墙数选源码分支：少于下限时增加 `max(1,floor(总墙下限/20))` 堵墙，并按箱子概率增加一对箱子/目标；达到上限时只加一对；其余阶段按迭代优先墙次数与墙概率选择增加墙或增加箱子/目标。
3. 完全保留加权参数：箱子按中心距离和周围实体加权；墙按边缘距离、邻墙、连接点与实体加权；目标按最近箱距离、附近目标与邻墙加权。邻域是方形范围，放置只使用空地，扫描及抽签采用行优先顺序。优先阶段判断的短路、分支概率及循环条件中的重复随机抽样均按源码执行。
4. 用 HTML 构造求解逻辑判定：每批最多50个状态，每100轮对整个队列进行稳定启发排序；子状态按启发值稳定排序，深度超过80跳过。玩家可达区合并；落在冻结墙角的已到位箱子按源码转为墙参与后续搜索。空箱布局没有推箱后继，返回未找到解，不作为可解中间布局保存。
5. 未找到解或达到求解限制就恢复上次保存布局，重新计算墙数；成功则保存整个布局。输出筛选失败也不撤销已求解的构造状态，下一轮仍从它继续。
6. 对结构匹配的候选另用项目现有 Push A* 求解，确认真实完整解答、最少推箱数及相同推箱数下的最少总移动。按推箱范围、原复杂度和批次排除集合筛选。
7. 合格候选按 HTML 质量比较：质量更高，或者质量差小于10分且源码解答推箱更长，就替换最佳。源码比较并不保证最佳分数单调上升。至少完成30轮后允许源码提前结束条件；可接受质量、推箱≥20、零起算迭代≥40且墙数达标时返回当前合格布局。其他情况运行至候选上限或预算结束，返回已完成验证的合格候选。

单关与批量共用读取、校验、构造、求解、复杂度和质量逻辑。批量只添加数量、`baseSeed + index×104729` 的逐关种子、输出去重与任务调度；排除集合不改变保存/回退轨迹。没有合格输出时记录失败，继续下一槽位。

## 参数与配置

生成尺寸为宽、高各5–8，包含外围墙；该范围只限制生成入口，已有大关卡的编辑、游玩和求解不受影响。默认：8×8、箱数自动、墙比例自动、**1–60次推箱**、普通复杂度、自动种子、400次候选、60秒总预算、每次构造/最终求解最多2秒。默认下限由旧20步改为1推，避免把较长行走路线错误等同于20次推动。填写的推箱范围始终严格执行。

0.13.1将单关/批量的生成难度改为Unity下拉框，选项为不限(0)、简单(1)、普通(2)、困难(3)。默认仍是普通；不限只跳过难度档位筛选，仍进行完整复杂度评估，关卡标签/元数据保存实际档位，请求参数单独保存difficulty=0。重新打开批量表单可恢复不限。按用户要求精简生成帮助文字，两者继续使用同一核心逻辑。

8×8沿用网页实际配置：墙概率0.5、箱子概率1.0、墙下限比例0.25、上限比例1.6、优先墙比例0.7、放置重试1400次、求解150000次、350000节点。36个内部格、28堵边界墙，对应总墙阈值37与85、优先墙44轮。**上限比例1.6是源码真实值；不改写成0.6，也不截断为1。**6×6、7×7使用对应原配置，5×5及没有专用配置的5–8矩形使用源码全局默认。内部保留9×9–11×11配置用于源码对照，当前生成入口会拒绝这些尺寸。

项目保留以下输入与输出约束，因此不能宣称在所有参数、机器上与无种子网页输出相同：

- 现有种子替换 `Math.random()`，相同版本/参数/种子在未触及时间限制时可复现。
- 箱子数留空自动；填写1–8时准确匹配。自动上限为 `min(8, floor((内部格数−固定墙数−1)/2))`，墙也自动时固定墙数按0算；实际布局仍必须容纳玩家和全部箱子/目标。移除旧面积/8软上限和按难度偏好1/2/3箱。
- 墙比例留空按 HTML 阈值与求解反馈增长，不再强加45%的自动上限或20%的软偏好。填写0–45%时按原四舍五入墙数匹配，0表示零内部墙。自动墙的物理上限预留至少一对箱子/目标或用户固定箱数及玩家。
- 达到箱数/墙数上限就停止增加该元素；不引入补偿移动或删除动作。房间可保留与玩家不连通的空白地面，沿用 HTML；完整解答仍须覆盖所有箱子的目标。
- 构造求解器保留源码启发式行为，可能因深度/资源限制漏掉可解布局。它的“未找到解”不用于给保存关卡写入严格无解结论。最终推箱范围依据项目 Push A* 的最少推箱数；质量依据源码构造求解的推箱长度，两者分别记录。
- 原复杂度作为额外输出筛选；任何预算或备用模板都不能自动放宽用户条件。显式取消丢弃本次候选；总预算到期只返回之前已完成所有验证的结果。
- 备用模板在主循环尚未找到可解状态且候选耗尽时尝试；源码此入口给至多1000毫秒，能选中房间、线性或最简模板，走廊模板不可达。模板声明的估算次数不作为证据；实际求解、范围和复杂度仍须通过。预算已经到期时不额外延长生成时间。模板保留多玩家标记时，按源码转换选最后一个玩家并清除其他标记。

精确参数与推箱/复杂度组合会缩小可接受结果范围，可能耗尽；尤其仅允许增加的构造过程可能停在某个已经可解的布局。此版本不再用自定义变异补救这个行为。

## 复杂度与 HTML 质量

原复杂度不变：`35×箱子依赖 + 30×腾挪/规划 + 20×空间争用 + 15×失败分支`，<25简单、25–<50普通、≥50困难。最多12次替代推动探查，找到更简单解时降低评分，未知分支不计为死路。复杂度与推箱次数是两个独立条件。

HTML质量版本 `html-quality-3.0`：推箱长度/模式35%、空间分布25%、方向变化20%、墙密度12%、解法效率8%，分数由源码0–1换算为0–100。长度以 `referencePushes+1`（包含起点）计算，基础阈值为 `floor(width×height×0.35)`。源码构造器总是用medium评估器，不随我们的目标复杂度切换。

源码 `StateNode` 没有 `direction` 和 `boxIndex`，实际方向全部回退到U，方向变化项为0、效率项为0.3；三步模式也据此计算。为复现真实择优行为保留这些值，未私自加入实际路径方向。旧地面使用率/墙结构/箱互动字段仅供读取历史JSON，新质量不使用它们。后续若修正这些源码占位指标，应作为明确的算法版本变更。

## 保存与兼容

关卡 schemaVersion保持1。新参数用 `parameterVersion=2`、`minPushes/maxPushes` 明确单位；旧 `minMoves/maxMoves` 仅保留为历史记录，检测到非零旧范围就拒绝直接重新生成，提示重新填写推箱次数。原关卡、解答、可信总移动 `verifiedMoves` 及游玩步数不受单位迁移影响。

生成记录仍保存种子、完整请求、实际布局、选中候选编号、尝试数、来源仓库/提交、复杂度、质量和完整解答。质量额外记录 `referencePushes` 与各 HTML 分项。内容编辑清除旧解答、复杂度和质量，保留来源。不会改写现有用户关卡、分类、排序、印章或草稿。
